# Мой трекер (lifeboard)

Личный трекер-конфигуратор: финансы и карты, тренировки и программы, курение, покупки для дома, записи к врачам и **свои трекеры** с произвольными полями. Mobile-first PWA: данные живут в IndexedDB браузера и работают офлайн. Аккаунт на своём сервере (GraphQL + MySQL в docker) — **необязательная** надстройка для синхронизации между устройствами.

## Стек и команды

- Svelte 5 (руны) + TypeScript + Vite. Без UI-библиотек, без роутер-библиотек, без chart-библиотек.
- `npm run dev` — dev-сервер (порт 5173, `--host` для проверки с телефона в той же сети)
- `npm run check` — svelte-check (должно быть 0 ошибок и 0 предупреждений)
- `npm run build` — сборка в `dist/` (статичные файлы, относительные пути — можно хостить где угодно)
- `npm run icons` — перегенерировать PNG-иконки из `scripts/gen-icons.mjs`
- TypeScript закреплён на 6.x: svelte-check пока не работает с TS 7.

Сервер и окружение (всё в docker, конфигурация — в `.env`, образец в `.env.example`):

- `npm run docker:dev` — вся связка: MySQL, GraphQL-сервер, vite и Mailpit (письма на http://localhost:8025)
- `npm run docker:api` — только MySQL и сервер, если фронт вы запускаете сами через `npm run dev`
- `npm run docker:prod` — боевая сборка: Caddy со статикой и TLS, сервер, MySQL, ежедневный mysqldump
- `cd server && npm test` — 45 тестов (vitest + fastify.inject), нужна поднятая MySQL
- `cd server && npm run check` — типы сервера; `npm run check:queries` — сверка GraphQL-запросов фронта со схемой
- `cd server && npm run cli -- <команда>` — инвайты и пользователи (в prod: `docker compose exec api node dist/cli.js`)

## Архитектура

- `src/lib/store.svelte.ts` — единое `$state`-хранилище `data` (коллекции-массивы + `settings`). Автосохранение в IndexedDB через `$effect` по каждой коллекции (debounce 300 мс + flush на `visibilitychange`/`pagehide`). CRUD-хелперы `add/find/update/upsert/remove`, справочники, реестр модулей, экспорт/импорт JSON.
- `src/lib/nav.svelte.ts` — hash-роутер (`router.path`, `go`, `goBack`, `replaceRoute`), стек нижних шторок (`openSheet/replaceSheet/closeSheet` — пишут в history, системная «назад» закрывает шторку), `toast`, `ask` (диалог подтверждения).
- `src/lib/types.ts` — все сущности. **Деньги — целые центы. Даты — локальная строка `YYYY-MM-DDTHH:mm`** (сравниваются как строки; периоды — `periodRange` + `inPeriod` из `utils.ts`).
- `src/App.svelte` — разбор маршрута и выбор страницы; рендерит `BottomNav`, `SheetHost`, тост и диалог.
- `src/modules/<module>/` — страницы и формы каждого раздела. Формы — компоненты шторок: принимают `close` и открываются через `openSheet(Form, props)`, верстка через `SheetFrame`.
- `src/data/` — стартовые справочники (категории, магазинные категории, специальности врачей, пресеты трекеров) и библиотека упражнений + шаблоны программ. **id встроенных упражнений стабильны** — на них ссылаются тренировки. У каждого пресета трекера есть `group`; `TRACKER_PRESET_GROUPS` собирает их в разделы в порядке объявления, конструктор рисует список по этим разделам.
- Стили — `src/app.css` (токены в `:root`, светлая тема через `[data-theme='light']`, утилитарные классы `.card .list .row .btn .chip .seg .stat …`).
- `src/lib/api.ts` — GraphQL-клиент на `fetch` (без библиотек), `src/lib/auth.svelte.ts` — состояние аккаунта, `src/lib/sync.svelte.ts` — синхронизация, `src/lib/webauthn.ts` — passkeys в браузере. Экраны: `src/pages/Auth.svelte`, `src/pages/Account.svelte`.
- `server/` — отдельный пакет: Fastify 5 + GraphQL Yoga + Pothos + Prisma → MySQL 8.4. Схема базы в `server/prisma/schema.prisma`, резолверы в `server/src/schema/`, логика входа в `server/src/auth/`.

## Связи между модулями

Курение (покупки), Покупки (чеки), Врачи (стоимость визита) и свои трекеры (поле «Деньги») создают операции в финансах через `syncLinkedTx()` — у операции есть `source: { module, refId }`, у записи-источника — `txId`. Служебные категории (`system: 'smoking' | 'groceries' | 'health'`) находятся через `systemCategoryId()`. При удалении операции ссылки снимаются (`removeTransaction`).

## Финансы: бюджеты и регулярные платежи

- `data.budgets` — месячные лимиты (`categoryId` пустой = на все расходы). Расчёт прогресса, остатка в день и прогноза — `budgetStatuses()` в `modules/finance/finance.ts`.
- `data.recurring` — подписки/аренда/зарплата. `processRecurring()` (store) при запуске и при смене дня создаёт операции с `source.module = 'recurring'` для `auto`-платежей и сдвигает `nextDate` через `advanceDate()` (поле `day` держит «якорное» число месяца). Ручные (`auto: false`) подтверждаются через `payRecurring()`.
- `frequentTx()` — частые операции для чипов в форме, `previousPeriod()/deltaPct()` — сравнение с прошлым периодом, `exportCsv()` — выгрузка (`;` + BOM для Excel).
- Страница `/stats` (`pages/Stats.svelte`) собирает сводку и автоматические выводы по всем включённым разделам.

## Свои трекеры: цели

`Tracker.goal` + `goalMode` ('min' | 'max') — дневная цель по первому полю «число/деньги/длительность» (иначе по числу записей). Логика в `modules/custom/tracker.ts` (`goalDayValue`, `goalMet`, `goalStreak`, `goalProgress`), отображение — `GoalProgress.svelte`.

Длительность задаётся в минутах, поэтому цель сна — `420`, а не `7`. `aggregate()` там же решает, складывать значения за день или брать последнее: показания (вес, давление, глюкоза, пробег) и единицы из `LAST_UNITS` — «последнее», остальное — сумма. Новый пресет с показанием нужно либо назвать так, чтобы он попал в этот список, либо добавить его единицу в `LAST_UNITS`.

## Модули и «конфигуратор»

`settings.modules` — упорядоченный список `{ id, enabled }`: встроенные (`finance`, `workouts`, `smoking`, `groceries`, `health`) и `tracker:<id>` для своих трекеров. Порядок = порядок карточек на главной. Новый встроенный модуль: добавить id в `BUILTIN_MODULE_IDS` и `BUILTIN_MODULES`, маршрут в `App.svelte`, виджет в `pages/Home.svelte`, действия в `pages/QuickAdd.svelte`, при необходимости — в `History`/`Calendar`.

## Аккаунт и синхронизация

Приложение остаётся offline-first: без аккаунта всё работает как раньше. Если сервер доступен (`/graphql` на том же origin), в настройках появляется раздел «Аккаунт».

- **Синхронизация — коллекциями целиком.** Сервер не знает модель трекера: коллекция (`transactions`, `settings`, …) лежит в `SyncCollection` как JSON с номером ревизии. Поэтому `types.ts` не требует `updatedAt`/tombstone'ов.
- Клиент (`sync.svelte.ts`) хранит в IndexedDB под ключом `_sync` свой `deviceId` и по каждой коллекции `{ rev, checksum }`. Решение «отправлять или нет» принимается по **своей же** контрольной сумме: MySQL возвращает JSON с другим порядком ключей, поэтому серверную сумму сравнивать нельзя.
- Пуш идёт с `baseRev`. Если на сервере ревизия другая — возвращается конфликт с серверной версией, запись **не** перетирается; выбор делает человек в `Account.svelte` (`resolveConflict`), прошлая версия всегда остаётся в `SyncRevision`.
- Первый вход на устройстве, когда данные есть и локально, и в аккаунте, не склеивается автоматически — показывается выбор (`chooseFirstSync`).
- Синхронизация включается только при `app.ready` (иначе на сервер уедут пустые коллекции до загрузки из IndexedDB).

## Вход и безопасность

- Пароли — argon2id (19 МиБ, 2 прохода). Сессия — случайный токен в cookie `__Host-sid` (в dev по http просто `sid`), в базе только его sha256. Новая сессия создаётся при каждом изменении прав: вход, второй фактор, смена пароля.
- Регистрация по инвайт-коду; `AUTH_OPEN_REGISTRATION=true` в `.env` включает открытую регистрацию с подтверждением почты и сбросом пароля (нужен `SMTP_URL`). Первый аккаунт в пустой базе становится администратором.
- Второй фактор: TOTP (секрет шифруется AES-256-GCM ключом `ENCRYPTION_KEY`, использованный шаг запоминается от повтора) и 10 одноразовых кодов восстановления. Passkeys — полноценный вход без пароля.
- Перебор: не больше 5 неудач на аккаунт и 20 на IP за 15 минут (`LoginAttempt`), плюс задержка на неудачном ответе. События безопасности пишутся в `AuditLog`.
- CSRF закрыт проверкой `Origin`/`Sec-Fetch-Site` — фронт и API живут на одном origin, поэтому CORS не нужен. `APP_ORIGIN` может перечислять несколько адресов через запятую (нужно для проверки с телефона по локальной сети); первый — основной, он идёт в ссылки писем и в проверку passkeys.
- Контрольная сумма коллекций считается через `crypto.subtle`, а по http в локальной сети его нет — поэтому есть запасной быстрый хэш (`weakHash` в `sync.svelte.ts`) с префиксом алгоритма в сумме. Криптостойкость тут не нужна: сумма сравнивается только со своей же.

## Уведомления

Push-уведомления своими ключами VAPID, без сторонних сервисов. Выключены, пока в `.env` нет
`VAPID_*` (как и почта без `SMTP_URL`) — остальное работает как обычно.

- **Расписание считает клиент.** `src/lib/reminders.ts` → `planReminders()` собирает план на 7 дней
  (цели и лимиты, регулярные платежи, бюджеты от 80%, тренировки за час, визиты накануне и за два часа),
  переводит местное время в UTC и отправляет через `setReminders`. Сервер (`server/src/push/scheduler.ts`)
  раз в минуту смотрит, чему пора, и доставляет — модель трекера ему по-прежнему не нужна.
- У напоминания есть стабильный ключ вида `goal:<trackerId>:<дата>`, уникальный на пользователя.
  `setReminders` заменяет набор целиком: чего в плане больше нет — удаляется (цель закрыли),
  а `sentAt` у уже отправленных не сбрасывается, иначе уведомление ушло бы повторно.
  План переотправляется после каждой синхронизации (`uploadPlan` в `done()`), но только при изменениях.
- Тумблеры живут в `settings.notify` и поэтому синхронизируются между устройствами; подписка
  (`PushSubscription`) привязана к устройству. Подписки, на которые служба ответила 404 или 410, удаляются.
- **Service worker регистрируется только в prod-сборке**, поэтому уведомления не проверить на dev-сервере —
  нужен `npm run preview` или боевой контур. На iPhone — только из приложения на экране «Домой».
- `VAPID_SUBJECT` обязан быть `mailto:` или `https://` без пробелов и угловых скобок: Apple иначе отвечает 403.

## Соглашения

- Интерфейс полностью на русском, обращение на «вы».
- Поля ввода не меньше 16px (иначе iOS зумит), цели касания ≥ 40px, учитывать `safe-area`.
- Новые поля данных — необязательные, с миграцией в `migrate()` (store), чтобы старые бэкапы импортировались.
- Предупреждение `state_referenced_locally` отключено намеренно: формы берут начальные значения пропсов один раз.
